## 1. 現状アーキテクチャ監査

```
[院内PC/タブレット(PWA)]                    [Vercel]                      [外部]
  Next.js App Router ──────────────── API Routes ──────────── Anthropic API（臨床AI 10系統）
  データ実体 = localStorage              /api/sync ───────────── Supabase（全キー同期の保管庫）
  （患者・カルテ・プロトコル全部）        /api/marketing/* ────── LINE Messaging API
                                        /api/liff/verify ────── LINE公式（IDトークン検証）
[Google Apps Script 予約システム] ──── /api/yoyaku/feed（読取プロキシ）
  スプレッドシート＝予約DB               reservation-notify（患者LINE通知）
```

重要な設計事実：

- **臨床データのDBはサーバーに無い。** すべて各端末の localStorage にあり、
  クラウド（Supabase）は「localStorage 全キーの丸ごとコピー」を1つ保管しているだけ
- 同期は【起動時: クラウド→端末へ全上書きプル】＋【保存時: 端末→クラウドへ全プッシュ】。
  マージ・タイムスタンプ比較・履歴は無い（＝後勝ち。2026-08-08にAI文章消失として実害が出て、
  プッシュ漏れは修正済み。ただし「全上書き」構造自体は残っている）
- 認証はクライアント側のみ（本番はサーバー側で画面・APIを守っていない）。
  恒久対応（サーバー認証）はローカルで作業中・未コミット
- プロトコルはテンプレートから**患者ごとにコピー**して保持
  → 指示書が求める「プロトコル更新が過去患者に波及しない」性質は**既に満たしている**

## 4. データ構造分析

- 全キー一覧と件数は `ROLLBACK.md` §5 のとおり（34キー）
- 患者は2系統: `pt_patients`（カルテ・82名）と `protocolPatients`（プロトコル患者・40名）。
  `linkedPatientId` で連結（氏名一致の自動推定あり）。**照合エンジンはこの連結を前提にする**
- 評価データも2系統: プロトコル側 `protocolAssessments`（メトリクス汎用・2件と少ない）と
  カルテ側 `pt_rom_records`・`pt_special_tests`・復帰基準テスト等（こちらが実運用の主）。
  → **基準×実測の照合は「カルテ側の実測」を正とする**
- 型は `src/types/*.ts` に集約済みで拡張しやすい。ストアは全て「1キー=1配列」の単純構造

## 5. リスク分析（正直な優先順位）

| # | リスク | 深刻度 | 指示書との関係 |
|---|---|---|---|
| R1 | **同期が「全上書き・後勝ち」**。複数端末同時使用や push 失敗時に編集が消える構造は残存（今回のAI文章消失はこの症状） | 高 | 「患者データ不整合」を防ぐ土台。次世代機能を積む前に緩和すべき |
| R2 | **本番にサーバー側認証が無い**（アプリ画面・同期API・AI APIが事実上公開。同期シークレットは公開バンドルに同梱） | 高 | 指示書のRBAC・監査ログ・暗号化以前の前提問題。恒久対応（サーバー認証）はローカル作業中 |
| R3 | 予約管理の管理者パスワードがクラウド同期に載っている（`yoyaku_feed_key`） | 中 | 同期の除外キーに追加すべき |
| R4 | localStorage容量（現在1.3MB＋添付base64。上限目安5〜10MB） | 中 | 添付・画像が増えると限界。行DB移行の動機 |
| R5 | GASの手作業デプロイ（貼り替え事故は仕組みで対策済みだが構造は残る） | 低〜中 | 変更頻度を下げる運用でカバー |

**指示書のセキュリティ要件（RBAC・監査ログ・保存時暗号化・アクセス失効…）は、
localStorage主体のままでは実現不可能。** 本気で満たすには「Supabaseの行レベルDB＋サーバー認証」への
移行が前提になる。これが次世代化の最大の構造的決断点。

## 6. 次世代アーキテクチャ案

中心コンセプト（指示書どおり）: **PROTOCOL → PATIENT → ASSESSMENT → STATUS → GOAL → CRITERIA → NEXT ACTION**

```
[既存プロトコル(標準)]     [新規: criteria-engine (純関数lib)]      [既存カルテの実測]
 phases.advanceCriteria ──▶ 基準キーと実測値のマッピング ◀── ROM/筋力/NRS/復帰基準テスト
                              │ 達成 ✅ / 未達 ⚠ / 未評価 ❔
                              ▼
      [患者ダッシュボード first view] ── [患者説明モード(全画面・専門情報OFF)]
      [AIコパイロット: 照合結果+履歴 → JSON出力 → AI提案/承認済みの2状態]
```

- **新設は「接続層」**（criteria-engine・Problem List・Goal二層・説明モード）。既存画面は壊さない
- Feature Flag: `src/lib/feature-flags.ts`（環境変数＋設定画面のON/OFF）で
  `EXPLANATION_MODE / SMART_PROTOCOL / AI_SUMMARY_V2 / REASSESSMENT_ENGINE / SAFETY_CHECK` を個別制御
- AI: 既存ルートを流用しつつ、出力を指示書§18のJSONスキーマに統一。
  `aiStatus: 'suggested' | 'approved'` を持たせ、**承認までは正式記録にしない**
- データ基盤は2段階:
  - **段階A（すぐ）**: 同期にキー別タイムスタンプを付けてマージ化（全上書き廃止）＋秘密キーの同期除外
  - **段階B（本命・別プロジェクト級）**: Supabase行DB＋サーバー認証＋監査ログ。段階Aまでの構造で
    新機能は全て動くため、Bを待たずに臨床価値を出せる
